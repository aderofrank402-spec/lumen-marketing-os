# Department 2 — Lead Generation & Qualification

Department 2 runs on this local machine and uses the existing SQLite database, queue, outbox, pause controls, and audit log. It implements 2A (Lumen enrichment), 2B (fit-score gate), and 2C (decision-maker research). **No Lumen or Hunter calls are enabled by default; no outreach is sent.** The Lumen Sieve product itself is not hosted by this OS.

## Operator sequence

1. Complete Department 1 research review. Promote only a real organization with a sourced canonical domain using `lmos research promote-organization ...`.
2. Run `lmos qualification consume` (or `qualification run`) to turn the `qualification.discovery` outbox event into a durable `needs_review` intake. Inspect `qualification report`; reject false identities with `qualification reject-intake INTAKE_ID --reviewer NAME --reason TEXT`.
3. Decide the initial target segment and rubric. Edit `config/qualification.json`: use a new `rubric_version`, set `rubric_status` to `approved`, and list only genuinely approved segments. Then run `qualification approve-rubric --reviewer NAME`. The version and exact configuration hash are audited; changing an approved version is refused.
4. Approve a specific sourced 1A/1B problem with `qualification approve-use-case FINDING_ID --vertical SEGMENT --problem TEXT --buyer TEXT --reviewer NAME`. This approves a market hypothesis, not every company in the segment.
5. Admit an intake with `qualification admit INTAKE_ID --segment SEGMENT --reviewer NAME --country-code KE --use-case-id CASE_ID --pain-evidence-url URL --pain-evidence-note TEXT`. The pain URL/note must show why this **particular organization** has the problem. Without a linked use case, the prospect may be enriched but will remain in fit review. A verified company domain is required; 2A uses Lumen's domain lookup so country is optional.
6. Once the product API is live and an authorized key exists, set `LUMEN_API_BASE_URL` and `LUMEN_API_KEY` in ignored `.env`, set `LMOS_ALLOW_LUMEN_LOOKUPS=true`, and set a deliberate positive `lumen_max_lookups_per_day` in `config/qualification.json`. Run `lmos qualification run` repeatedly or schedule it locally. Never put keys in Markdown, logs, Codex role files, or Git. A 202 starts a durable poll; only a validated 200 creates a snapshot. The configured 240-second deadline is an operational default, not a claim that every lookup always completes within it.
7. Review `qualification report` and `qualification prospect PROSPECT_ID`. A mismatch or missing evidence goes to review; the fit assessment retains factor-by-factor reasons and the rubric hash. If you later approve the use case or a revised rubric, use `qualification link-use-case ...` and `qualification rescore PROSPECT_ID --reviewer NAME`; rescore uses the saved snapshot, not another paid lookup.
8. For contacts, either add a public, named business contact with `qualification add-contact PROSPECT_ID --name NAME --role ROLE --email ADDRESS --source-url URL --reviewer NAME`, or explicitly enable and budget Hunter Domain Search in `config/qualification.json` and supply `HUNTER_API_KEY` in `.env`. Hunter results are **candidates**, never automatically verified. The provider's [Domain Search documentation](https://hunter.io/api-documentation) describes its fields and credit use; check the current plan and price before enabling it. Use `qualification verify-contact CONTACT_ID --prospect-id PROSPECT_ID --source-url URL --reviewer NAME` only after checking the named role and source. This creates a `content.review` handoff, not a message.

Use `./.venv/Scripts/lmos.exe` in PowerShell from this workspace root (or `python -m lumen_marketing_os` from an installed environment). `qualification tick` only enqueues due work, `qualification work` handles one queued job, and `qualification run` consumes handoffs then drains available Department 2 jobs. The local OS is not a perpetual service unless a scheduler runs these commands.

## Failure and safety rules

- Admission and fit are separate decisions. A directory listing, a generic company email, a matched domain, or a high profile-confidence score alone cannot qualify a prospect.
- Lookup attempts are written before the network call. Retries reuse the same Lumen idempotency key. Cold lookups are polled without holding a worker for minutes. Attempts, snapshots, score explanations, provider budget reservations, contacts, and outbox events survive process restarts.
- A network or provider failure is recorded distinctly from `not_found`, ambiguity, and deadline expiry. Paid contact queries are capped per UTC day; an uncertain Hunter call is held for review rather than repeated automatically.
- A terminal enrichment failure is not silently recharged. Reconcile the earlier provider outcome, then explicitly run `qualification retry-lookup PROSPECT_ID --reviewer NAME --reason TEXT --provider-effect-reconciled`; the next run uses a new attempt and a new daily-budget reservation.
- No contact is auto-verified. No content drafting, sending, public posting, or direct messaging is performed by Department 2. Downstream departments must enforce their own approval, suppression, contact validity, and platform rules.
- This build's Lumen/Hunter adapters are tested with fixtures, not live credentials; live provider compatibility and any actual paid quota remain unverified until you connect them. The default rubric is deliberately a draft because we have not approved an ICP together.
